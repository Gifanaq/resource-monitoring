# TPUMON

Сервис мониторинга ресурсов ТПУ. Проверяет настроенные HTTP/HTTPS-адреса, рассчитывает статус по истории проверок и отдаёт последние результаты через REST API. Для HTTPS отдельно проверяет срок действия TLS-сертификата.

Текущее демо хранит результаты в памяти: после перезапуска статусы начинаются с `UNKNOWN`. ORM и начальная миграция PostgreSQL подготовлены, но мониторинг пока не использует БД. Для запуска API PostgreSQL не требуется.

## Требования

| Вариант | Что установить заранее |
| --- | --- |
| Docker | Docker Engine, Docker Compose v2, Make; Docker daemon должен быть запущен и доступен пользователю |
| Локальный запуск | Python 3.13, Poetry 2.x, Make |
| TLS-интеграционные тесты | Дополнительно OpenSSL в `PATH` |
| PostgreSQL-интеграционные тесты | Дополнительно отдельный экземпляр PostgreSQL; проверено на PostgreSQL 17 |

Все команды выполняются из корня репозитория.

## Быстрый запуск через Docker

### 1. Создать настройки

```sh
cp -n .env.example .env
```

В `.env` уже заданы `APP_NAME=tpumon`, `APP_ENV=dev` и `API_PORT=8000`. При необходимости измените название приложения и внешний порт. Compose задаёт окружение `prod`, а dev-конфигурация — `dev`. PostgreSQL для запуска не требуется.

Добавьте в `.env` список HTTP-ресурсов для мониторинга. Здесь «сервис» — контролируемый сайт или HTTP-эндпоинт, а не контейнер Docker Compose.

Откройте `.env` и задайте настройки. Существующие строки изменяйте, не дублируйте их. Пример содержимого `.env`:

```dotenv
API_PORT=8000
APP_NAME=tpumon
CHECK_INTERVAL_SEC=60
SERVICES='[{"name":"Demo","url":"https://example.org","expected_status":200,"follow_redirects":true,"timeout_sec":10,"slow_response_ms":2000,"tls_warn_before_days":14}]'
```

`example.org` здесь — демонстрационный внешний адрес. Замените его адресом нужного ресурса. Дополнительные сервисы добавляются объектами в тот же JSON-массив. JSON записывается одной строкой; ключи и строковые значения заключаются в двойные кавычки, логические значения — `true` и `false`.

Без `SERVICES` используется пустой список: приложение запускается, а `/services` возвращает `[]`.

`.env` исключён из Git. Не помещайте в репозиторий рабочие пароли и токены. Переменные окружения процесса имеют приоритет над значениями из `.env`; префикс `TPUMON_` для настроек приложения не используется.

### 2. Собрать и запустить

```sh
make prod
```

Команда собирает образ и запускает API в фоне. В текущем Compose запускается только API, без PostgreSQL.

| Адрес при `API_PORT=8000` | Назначение |
| --- | --- |
| <http://localhost:8000/health> | Проверка процесса API |
| <http://localhost:8000/services> | Последние статусы сервисов |
| <http://localhost:8000/docs> | Swagger UI для ручного тестирования |
| <http://localhost:8000/openapi.json> | Контракт OpenAPI |

Если изменён `API_PORT`, замените порт в адресах. `/health` возвращает `{"status":"ok"}` и не подтверждает доступность контролируемых ресурсов или БД.

Проверка запуска и просмотр логов:

```sh
docker compose ps
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8000/services
make logs
```

`make logs` показывает поток логов; `Ctrl+C` завершает просмотр, оставляя контейнер работающим.

### 3. Применить изменения настроек или остановить

После редактирования `.env` повторите `make prod`: Compose пересоздаст контейнер при изменении передаваемых настроек. Перезапуск приложения сбрасывает результаты в памяти.

Остановка:

```sh
make down
```

## Разработка через Docker

Запуск с монтированием `src/`, автоматической перезагрузкой кода и debug-логами Uvicorn:

```sh
make dev
```

API остаётся доступен на `API_PORT`. При перезагрузке процесса накопленное состояние сбрасывается. Изменение `.env` требует повторного запуска Compose; одного сохранения Python-файла недостаточно.

Для остановки нажмите `Ctrl+C`. Остановка и удаление dev-контейнеров:

```sh
docker compose -f docker-compose.yml -f docker-compose.dev.yml down
```

## Запуск без Docker

Подготовьте `.env` по примеру выше. Установите зависимости и запустите приложение:

```sh
make install
make run
```

`make run` использует `--reload`; API доступен на <http://127.0.0.1:8000>. Остановка — `Ctrl+C`. Логи выводятся в терминал.

`API_PORT` используется только Docker Compose. Для другого порта при локальном запуске задайте его Uvicorn явно:

```sh
poetry run uvicorn src.main:app --reload --host 127.0.0.1 --port 8080
```

## Настройки

### Общие переменные

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SERVICES` | `[]` | JSON-массив настроек сервисов |
| `CHECK_INTERVAL_SEC` | `60` | Целое не меньше 60: пауза после завершения цикла конкретного сервиса; 300 задаёт 5 минут |
| `APP_NAME` | `tpumon` | Название API в OpenAPI/Swagger |
| `APP_ENV` | `dev` | Метка окружения; Compose задаёт `prod`, dev-override — `dev` |
| `API_PORT` | `8000` в Compose | Внешний порт контейнера; не настройка Uvicorn при `make run` |

### Поля элемента `SERVICES`

| Поле | По умолчанию | Допустимые значения и смысл |
| --- | --- | --- |
| `name` | Обязательно | Непустое название сервиса |
| `url` | Обязательно | URL с протоколом `http://` или `https://` |
| `expected_status` | `200` | Ожидаемый HTTP-код от 100 до 599 |
| `follow_redirects` | `true` | Следовать HTTP-редиректам; для проверки самого кода 302 задайте `false` |
| `timeout_sec` | `10` | Положительное конечное число, допускает дробную часть; таймаут сетевых операций HTTPX и общий таймаут подключения/handshake TLS |
| `slow_response_ms` | `2000` | Положительное целое; успешный ответ медленнее этого порога даёт деградацию |
| `tls_warn_before_days` | `14` | Положительное целое: за сколько дней предупреждать об окончании сертификата |

`failure_threshold=3` и `recovery_threshold=2` сейчас заданы в доменной сущности `Service`. Передача этих полей в `SERVICES` их не меняет: загрузчик настроек пока их не поддерживает.

## Как выполняются проверки

Для каждого сервиса создаётся независимая фоновая задача. Первый цикл запускается сразу после старта; следующий — через `CHECK_INTERVAL_SEC` после завершения предыдущего. Например, цикл длительностью 10 секунд при интервале 60 секунд даёт около 70 секунд между началами циклов.

HTTP и TLS одного сервиса выполняются параллельно. В API публикуется результат завершённого цикла. Медленный или недоступный сервис не задерживает опрос остальных.

### HTTP

- HTTP-успех — полученный код совпадает с `expected_status`.
- Сетевые ошибки и таймауты повторяются ещё три раза, с паузами 5, 10 и 15 секунд. Максимум — четыре попытки.
- Полученный HTTP-ответ фиксируется сразу, даже если это 404 или 503. Такой код сам по себе не вызывает повторных попыток.
- Серия попыток считается одной проверкой для счётчиков гистерезиса.
- `response_time_ms` относится к попытке, которая получила HTTP-ответ; паузы повторов и отдельная TLS-проверка в него не входят. При исчерпании сетевых попыток HTTP-код и время ответа равны `null`.
- `timeout_sec` не является общим пределом длительности всей серии HTTP-попыток. При следовании редиректам время полученного ответа включает переходы.

Отклонение HTTP-кода от ожидаемого может сопровождаться `error: null`: поле `error` предназначено для исключений, а полученный ответ представлен в `status_code`.

Успешный ответ страницы входа не подтверждает работу функций сервиса после авторизации.

### TLS-сертификат

Проверяется исходный HTTPS hostname и явный порт из `url`, иначе порт 443. Цепочка редиректов для TLS не исследуется. Для исходного HTTP-адреса результат — `NOT_APPLICABLE`, даже если HTTP перенаправляет на HTTPS.

| `tls.state` | Значение |
| --- | --- |
| `NOT_CHECKED` | Первый цикл ещё не завершился; поля TLS-результата равны `null` |
| `NOT_APPLICABLE` | Исходный URL использует HTTP; время проверки есть, сертификата нет |
| `VALID` | Сертификат прошёл проверку, до окончания больше заданного порога |
| `EXPIRING` | Осталось не больше `tls_warn_before_days`, включая точное равенство |
| `ERROR` | Ошибка сертификата, DNS, соединения, таймаут или отсутствие доступной даты окончания |

Доверие сертификату и соответствие hostname проверяются. При просроченном, недоверенном сертификате или неверном имени дата окончания может быть неизвестна и возвращается как `null`. Предыдущая удачная дата не выдаётся за результат новой неуспешной проверки. Выполняется одна TLS-попытка за цикл, без повторов.

Самостоятельный TLS-результат пока не меняет общий цвет. При этом HTTPS-запрос HTTP-проверки тоже проверяет сертификат: его собственная SSL-ошибка может сделать HTTP-проверку неуспешной и повлиять на цвет.

## Гистерезис статуса

Гистерезис удерживает подтверждённый статус при кратковременном восстановлении и учитывает серии HTTP-результатов. Текущие пороги: **3 ошибки подряд до RED, 2 успеха подряд для восстановления**. Успехом считается ожидаемый HTTP-код, включая медленный ответ.

| Статус | Смысл |
| --- | --- |
| `UNKNOWN` | Ещё нет завершённого первого цикла |
| `GREEN` | Ожидаемый HTTP-код и время ответа не больше порога; условие восстановления выполнено, если оно требовалось |
| `YELLOW` | Единичные ошибки, медленные ответы либо ожидание подтверждения восстановления |
| `RED` | Зафиксирована серия из трёх ошибок; статус удерживается до подтверждённого восстановления |

После каждого цикла сначала обновляются счётчики: ошибка увеличивает серию ошибок и обнуляет серию успехов; успех делает наоборот. Затем применяются правила в таком порядке:

1. Три ошибки подряд или больше → `RED`.
2. Ошибка до порога → `YELLOW`; если уже был `RED`, он удерживается.
3. При успехе после `YELLOW`/`RED`, если в текущей серии ещё меньше двух успехов, предыдущий цвет удерживается.
4. Иначе медленный успех → `YELLOW`, быстрый успех → `GREEN`.

Медленный ответ — **строго больше** `slow_response_ms`. При пороге 2000 мс ответ за 2000 мс не считается медленным, за 2001 мс — считается.

### Примеры

Каждая строка начинается с нового состояния `UNKNOWN`. Обозначения: **Б** — ожидаемый код за 100 мс; **М** — ожидаемый код за 3000 мс; **О** — ошибка/неожиданный код. Каждая буква — завершённый цикл, включая все его HTTP-повторы.

| Сценарий | Циклы | Цвет после каждого цикла |
| --- | --- | --- |
| Первый быстрый успех | Б | GREEN |
| Единичная ошибка и восстановление | Б → О → Б → Б | GREEN → YELLOW → YELLOW → GREEN |
| Недоступность и восстановление | О → О → О → Б → Б | YELLOW → YELLOW → RED → RED → GREEN |
| Ошибка прервала восстановление | О → О → О → Б → О → Б → Б | YELLOW → YELLOW → RED → RED → RED → RED → GREEN |
| Чередование ошибки и успеха | О → Б → О → Б → О → Б | YELLOW → YELLOW → YELLOW → YELLOW → YELLOW → YELLOW |
| Медленные успехи и быстрый ответ | М → М → М → Б | YELLOW → YELLOW → YELLOW → GREEN |
| Восстановление медленными ответами | О → О → О → М → М → Б | YELLOW → YELLOW → RED → RED → YELLOW → GREEN |

Медленные ответы тоже накапливают успехи. Поэтому после нескольких медленных успешных ответов одного быстрого достаточно для `GREEN`: счётчик успехов уже достиг порога. Требования «два быстрых ответа подряд» в текущем алгоритме нет.

После `RED` возможен прямой переход в `GREEN`; обязательной промежуточной стадии `YELLOW` нет. Если во время восстановления снова приходит ошибка, серия успехов обнуляется, а `RED` сохраняется.

## REST API и ручная проверка

`GET /services` возвращает JSON-массив последних результатов из памяти. Сам запрос не запускает новый опрос: повторный вызов в Swagger показывает то же состояние до завершения следующего фонового цикла.

Условный пример ответа после успешной проверки; даты сертификата приведены для иллюстрации формата:

```json
[
  {
    "id": 1,
    "name": "Demo",
    "url": "https://example.org/",
    "status": "GREEN",
    "changed_at": "2026-11-08T12:00:00Z",
    "last_checked_at": "2026-11-08T12:01:00Z",
    "status_code": 200,
    "response_time_ms": 120,
    "tls": {
      "state": "VALID",
      "checked_at": "2026-11-08T12:01:00Z",
      "expires_at": "2027-02-01T00:00:00Z",
      "error": null
    },
    "error": null
  }
]
```

`changed_at` меняется только при смене цвета. `last_checked_at` — время начала последней HTTP-попытки, результат которой сохранён; `tls.checked_at` относится к самостоятельной TLS-проверке и может отличаться. Время передаётся в UTC.

До завершения первого цикла общий статус — `UNKNOWN`, времена и HTTP-поля результата — `null`, TLS — `NOT_CHECKED`. Даже если HTTP уже ответил, общий результат цикла ждёт завершения TLS.

Для ручной проверки откройте `/docs`, выберите `GET /services`, нажмите **Try it out → Execute**. Проверьте название, URL, HTTP-поля, времена и `tls`. Для проверки ошибки ожидаемого кода можно временно задать другое значение `expected_status` у контролируемого тестового адреса и перезапустить приложение.

## Проверки кода и тесты

В репозитории нет pre-commit-хуков. CI выполняет Ruff, проверку форматирования, Mypy, pytest и отдельную сборку Docker.

```sh
make lint
poetry run ruff format --check .
make typecheck
SERVICES='[]' make test
```

Без `TPUMON_TEST_DATABASE_URL` PostgreSQL-тесты пропускаются. TLS-интеграционные тесты используют OpenSSL, временный тестовый CA и сервер на loopback; внешние ресурсы ТПУ не опрашиваются.

Автоформатирование и исправление линтера по необходимости:

```sh
make format
make fix-lint
```

### PostgreSQL-интеграционные тесты

Нужен отдельный тестовый экземпляр PostgreSQL и пользователь с правом `CREATEDB`. Тесты создают базы с уникальными именами `tpumon_test_*` и удаляют их после выполнения. Не используйте рабочий сервер БД для этих тестов.

Замените демонстрационные реквизиты своими тестовыми; специальные символы логина/пароля в URL должны быть URL-encoded. `TPUMON_TEST_DATABASE_URL` нужно передать именно как переменную окружения процесса — тестовый fixture не читает её из `.env`.

```sh
TPUMON_TEST_DATABASE_URL='postgresql+psycopg://test_user:replace_me@127.0.0.1:5432/postgres' \
SERVICES='[]' make test
```

В GitHub Actions PostgreSQL поднимается отдельным временным сервисом, тестовый URL передаётся автоматически. Режим доступа `trust` из CI не является настройкой для рабочего развёртывания.

## ORM и Alembic: отдельный этап

Подготовлены модели девяти таблиц: `categories`, `services`, `check_types`, `checks`, `http_check_settings`, `tls_check_settings`, `check_results`, `status_levels`, `service_statuses`. Начальная миграция `0001` создаёт их и справочники типов проверок/уровней статуса.

Применение миграции не переключает API на БД. PostgreSQL-репозиторий пока не подключён. Таблицы хостов и метрик относятся к следующему этапу TPUMON-4.

Для проверки миграций сначала подготовьте отдельную базу PostgreSQL и пользователя с правами создания таблиц. Добавьте в локальный `.env` реквизиты этой базы:

```dotenv
POSTGRES_USER=tpumon_user
POSTGRES_PASSWORD=replace-with-local-password
POSTGRES_DB=tpumon
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
```

Обязательны пользователь, пароль и название базы; hostname по умолчанию `localhost`, порт — 5432. Параметры читаются отдельно от настроек демо и не обязательны для запуска API.

Применение миграции и проверка соответствия ORM:

```sh
poetry run alembic upgrade head
poetry run alembic current
poetry run alembic check
```

Предварительный просмотр SQL без подключения к БД:

```sh
poetry run alembic upgrade head --sql
```

При последующих изменениях моделей создание ревизии выполняется против доступной БД с применёнными миграциями. Сгенерированный файл нужно проверить вручную: `--autogenerate` не заменяет ревью изменений схемы.

Пример для будущего изменения моделей:

```sh
poetry run alembic revision --autogenerate -m "describe schema change"
```

Миграции включены в Docker-образ, но автоматически не запускаются. Текущий Compose не создаёт PostgreSQL и не передаёт контейнеру `POSTGRES_*`; приведённые команды Alembic рассчитаны на локальное Poetry-окружение.

## Частые ситуации

| Симптом | Что проверить |
| --- | --- |
| `/services` возвращает `[]` | `SERVICES` не задан, содержит `[]` либо переопределён окружением процесса |
| Статус ещё `UNKNOWN` | Первый цикл не завершился: HTTP может делать повторы, TLS — ожидать таймаут |
| `YELLOW` сразу после запуска | Первый сбой или медленный ответ; проверьте HTTP-код, время и `error` |
| `RED` после одного успеха | Это удержание статуса до подтверждённого восстановления |
| TLS `NOT_APPLICABLE` | Исходный URL — HTTP; HTTPS-редирект не меняет применимость TLS-проверки |
| TLS `ERROR` | Проверьте доверие сертификату, hostname, порт, DNS и сетевую доступность |
| `error: null`, но HTTP-проверка неуспешна | Полученный `status_code` отличается от `expected_status` |
| После перезапуска история исчезла | Текущее хранение в памяти; ORM пока не подключена к мониторингу |
| Изменение `API_PORT` не влияет на `make run` | Для локального Uvicorn задайте `--port` явно |
| Порт Docker занят | Измените `API_PORT` в `.env` и повторите запуск |
| Docker daemon недоступен | Проверьте его запуск и права своего пользователя на Docker |
